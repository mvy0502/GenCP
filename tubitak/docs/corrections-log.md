# Corrections log

Every case where what was registered, claimed, or assumed diverged from what actually happened.
Kept in one place so the pattern is visible: the run is corrected or the record is corrected,
never neither. Companion to the withdrawn-claims list in [../README.md](../README.md).

The test applied throughout, stated once here:

> Would a reader who knew about this discrepancy interpret any result differently?

If no — correct the record, prominently, with the evidence. If yes, or if the discrepancy is
biased **toward** a registered prediction — correct the run. A bias against our own prediction
strengthens the result and may stand (disclosed); a bias toward it must be eliminated even when
probably immaterial, because "probably immaterial and pointing at our prediction" is exactly the
configuration a skeptical reader is entitled to reject.

## Why this log is tiered

A documentation slip, a lost artifact and a misstated registered check are not the same kind of
failure, and grading them identically invites a reader to discount the whole record by its worst
line rather than by its worst tier. The tiers below say which kind each entry is, so that
severity is read from the tier and not from the fact of appearing here at all. Nothing is
softened by the sorting: every entry keeps the wording it was written with, and an entry that
belongs in two tiers is split into two entries rather than filed under the lesser one — which is
what happened to the stop rule, entries 26 and 27.

**Tier 1 — deviations with substantive defences.** The protocol, the run, or the mechanism
diverged from what was registered or assumed. Each carries an argument and a disposition: the
run was corrected, the claim was withdrawn, or the deviation is defended on the evidence and
the defence is written down where it can be attacked.

**Tier 2 — unrecoverable artifacts.** Something needed to re-derive a reported number no longer
exists. These are the entries a sceptical reader should weigh most heavily, because no argument
can repair them, so each states explicitly **which reported numbers are consequently
uncheckable**.

**Tier 3 — reporting errors.** The runs were correct and the artifacts survive; a document
stated something the artifacts do not support. Cheap to fix, and listed anyway, because a
reader who finds one uncorrected is entitled to wonder what else was never checked.

## What would have caught each sooner

1. Reading KARIOS's own definition of `mean_x`/`mean_y` before comparing to it.
2. Not silencing stderr in a harness, ever; an assertion that every gate chip has a reference file.
3. Reading the optimizer construction (`optimizer_G`/`optimizer_D` share one `--lr`) before writing a rate-ratio justification.
4. Checking scene availability for all sites at registration time, not at preparation time.
5. Printing the effective LR per epoch in the training log (one line: `lambda_rule`'s output); any glance at it shows a zero. The symmetry claim would have been caught by writing the per-arm schedule out epoch by epoch — five minutes of arithmetic — before using it in a decision.
6. Byte-level comparison gates on ANY substituted data source, run before adoption (this is now the standing "transparency gate" pattern); reading osmium's docs on extract strategies rather than assuming config keys are honored.
7. Preflight from inside the running kernel (which is what caught it); sooner: never hard-coding a mount path the platform does not document as a contract.
8. Reading the CLI's slug-derivation warning as an error, not a suggestion.
9. A one-line CUDA smoke test (`torch.randn(2,2,device='cuda') @ ...`) in preflight instead of trusting `is_available()`; capability-vs-arch-list assertion now standard.
10. Copying any about-to-be-touched untracked file aside before running a tool that writes into its directory.
14. Reading the inference options against the model definition once: `not opt.no_dropout` + no `model.eval()` is two lines of code; and running any command twice and diffing before calling it "byte-verified". The pix2pix paper states the design in one sentence.
15. The regenerable-label audit that is now on the Phase F backlog — re-rendering each corpus input at gate time would have caught the stale renders the day the fix landed; recording render-path provenance beside every corpus artifact (the tool now does this) prevents the class.
16. Citing, in every results table, the config file of the runs it came from — the KARIOS config JSON sits beside every output; diffing that JSON against the governing registration before writing the table is one command. And treating a failed fix exactly like a failed run: E3-a's failure was disclosed, but the replacement configuration needed its own registration (or its own retrospective label) before its numbers were written down.
17. A completeness pass over the registration text at results-writing time: every registered protocol element either has an artifact or has a disclosed absence. The ORB omission survived because the results document was written from what ran, not diffed against what was registered.
19. The same completeness pass as 17, applied to *reporting form* and not only to execution: the registration named two band conversions and a distribution, the document carried one conversion and three medians. "Which registered outputs does this document not contain?" is a different question from "which registered runs happened?", and both must be asked.
20. Asking of every summary statistic: **what value could this have returned if the hypothesis were true?** An adjusted mean at the covariate means is the raw mean by construction; five minutes of algebra, or one synthetic covariate of pure noise as a negative control, exposes it. A mediation test that returns exactly 0% on three different covariate sets is reporting its own identity, not a result.
21. One `assert` that the refined output is not on the search lattice — or a single glance at the value column, where 930/930 integer hypots are visible without any tooling. A registered refinement step that leaves no trace in the numbers did not run.
22. Committing the harness beside the results, which entry 16's postscript already prescribed and the C4/C5 package adopted; and never letting a follow-up package extend an earlier package's scripts in place — copy them aside first (entry 10's lesson, unlearned).
23. A check at commit time that **every document a registration, an amendment or a results file links to is tracked** — one `git ls-files --error-unmatch` per link target. The handoff document had been relied on for two days as if it were in the record; nothing surfaced it until an amendment tried to link to it. Untracked is invisible: `git status` shows it once, in a list nobody re-reads.
24. Generating results tables **from** the summary artifact rather than retyping them beside it: every one of these three defects is a transcription step a reader cannot see. A one-line assertion that each printed value round-trips against its JSON field would have caught all of them, and the unreproducible SE column would have failed loudly instead of silently.
25. Writing a per-chip CSV for every scored package, without exception — the same convention B1, B2 and C45 followed in the same repository. Phase C is the earliest package and predates the habit; it is also the one the paper's primary comparison is registered against, which is the worst possible place for the gap.
26. Registering stop rules with a **threshold and a single governing test**, not a two-part rule with an unquantified verb. "Rising" fires on any positive difference; nobody intended that, so nobody applied it, and the rule silently became whatever the sharp half said. A rule that is never applied literally is not a rule — it is a note.
27. Separating the two questions a failed gate raises — *was the rule right?* and *did we say what happened?* — and answering them in that order, in different places. Entry 26's defence is sound and entry 27's error is real; had they stayed one entry, the defence would have read as an excuse for the misstatement, and a reader would have been right to distrust both.
28. A check that **every registered gate names both a threshold and the code that evaluates it**. A gate specified in prose alone is not a gate; it is an intention. Two packages carried this one as an active divergence test, and the question that exposed it — "what number does it fire at?" — takes one minute to ask of any registration and had never been asked of this one.
29. **Every property the invariance table asserts needs a corresponding preflight capture, or the assertion is unfalsifiable.** That is the lesson across all of this entry's instances — image version, enumeration order, and arguably the seed-42 code path: each was asserted as held and none was recorded, so none could be checked afterwards. An invariance that cannot be checked after the fact is not an invariance, it is a hope. `pip freeze` and the ordered file-list hash are the first two implementations, both one line each. The tell was that the invariance table named a specific torchmetrics version - precise enough to look verified, while everything around it went unrecorded.
